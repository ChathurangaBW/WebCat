# WebCat project review

Reviewed commit: `5dff52d` ("Add native Burp MCP adapters and guarded agent tools")
Date: 2026-07-29
Scope: full repository — architecture, safety controls, CLI, tests, CI, docs.

> **Status: all findings resolved.** Every item below (H1–H3, M1–M6, and the low-severity and
> QA/documentation items) has been fixed on this branch, each with regression tests. See
> [CHANGELOG.md](../CHANGELOG.md) for the change list and `test/policy-regressions.test.mjs`
> for the paired allow/deny coverage. This document is retained as the original assessment
> and rationale.

## 1. Verdict

WebCat is a genuinely well-shaped project. The threat model is stated honestly, the code
is small (~2,700 lines, zero runtime dependencies), the deny-first policy gateway is a real
architectural boundary rather than a prompt instruction, and `npm run qa` passes cleanly
end to end (lint, contracts, 27 tests, build, smoke, relocation, branding ×2) in ~5 s.

The weaknesses are not structural; they are in the *sharpness* of the individual controls.
Several of the deterministic guards are weaker than the README claims, and in three cases a
plausible operator or MCP-server mistake produces a silent fail-open rather than a rejection.
For a tool whose entire value proposition is "the policy gate is trustworthy", those are the
issues worth fixing before anything else.

Priorities: **fix H1–H3 before any real engagement use**, then M1–M6, then the rest.

---

## 2. What is done well

- **The guard is a real chokepoint.** `SwarmOrchestrator` hands the provider an `executeTool`
  closure that only reaches `McpGuard.call`; the model never touches a transport. Policy
  errors are returned to the model as tool output rather than thrown into the loop, and the
  system prompt frames them as final. This is the right shape.
- **Ordering of checks in `evaluateScope` is correct**: authorization window → deny → allow →
  mode → risk policy. Deny genuinely precedes allow, and placeholder authorization
  (`REPLACE_...`) is rejected, so a freshly `init`-ed project cannot act externally.
- **`hostMatches`** is wildcard-safe in the way that matters: `*.example.test` requires a dot
  boundary and excludes the apex, so `notexample.test` and `evilexample.test` do not match.
- **Audit chaining** (`previousHash` + sha256 over the ordered core) with a serialized append
  queue, and the accompanying concurrency test, is more rigor than most tools of this size.
- **Capability-scoped tool exposure.** A profile only ever sees MCP tools whose *trusted*
  capability string is in its declared list, so `report-writer` cannot be handed `http.execute`
  even if the model asks. Combined with `maxAgentTurns` / `maxToolCallsPerAgent`, the blast
  radius per agent is bounded.
- **Burp adapter work is thorough.** Three server families, five presets, per-family capability
  maps, dangerous tools disabled by default, and argument-sensitive reclassification
  (`classifyBurpCall` downgrades `burp_config` to passive only for read actions). The
  `targetFromRawRequest` / `targetFromServiceFields` extraction handles the awkward reality
  that Burp tools pass hostname+port+TLS separately from the raw request bytes.
- **Zero runtime dependencies** and platform path centralization in `identity.mjs` / `paths.mjs`,
  with a relocation regression test. Supply chain surface is essentially nil.

## 3. High severity

### H1 — Allow rules fail open on missing or malformed fields
`src/scope.mjs:ruleMatches`

Every field check is `if (Array.isArray(rule.x) && rule.x.length > 0 && !match) return false`.
An absent, empty, or wrong-typed field therefore matches *everything*. Verified:

```js
allow: [{ id: "oops" }]                        // → https://bank.example.com/transfer ALLOWED (active)
allow: [{ id: "oops2", hosts: [] }]            // → any host ALLOWED
allow: [{ id: "t", hosts: "app.example.test" }]// → string instead of array; https://evil.test/ ALLOWED
```

The third case is the dangerous one: a plausible hand-editing typo (string instead of array)
in `engagement.json` converts a single-host engagement into an allow-all engagement, and
`validateEngagement` does not catch it — it only checks that `allow` is a non-empty array.

**Fix:** validate allow-rule shape in `validateEngagement` (each rule must be an object with at
least one of `hosts`/`paths` present, every present field must be an array of strings/numbers,
reject unknown keys), and make `ruleMatches` require an explicit `hosts` match rather than
treating absence as a wildcard. Add both an allow-test and a deny-test per `CONTRIBUTING.md`.

### H2 — Heuristic classification of untrusted tools defaults toward `passive`
`src/mcp.mjs:classifyTool`

Risk is inferred from `${tool.name} ${tool.description}` — and the description is supplied by
the MCP server, which the security model explicitly treats as untrusted. `PASSIVE_PATTERN`
matches the substrings `history`, `sitemap`, `scope`, `project`, `environment` *anywhere* in
that text. Verified classifications for an unmapped server:

| tool | description | classified |
|---|---|---|
| `exec_command` | "Runs a command; see scope and history" | **passive** |
| `send_payload` | "list history" | **passive** |
| `set_project_options` | *(none)* | **passive** |

`passive` implies `requiresTarget: false`, no approval, and — because the guard's trust check is
`if (!trusted && risk !== "passive") throw` — **execution**. Confirmed end to end: a call to
`exec_command` with `{cmd: "rm -rf /tmp/x"}` reached `manager.call` under `mode: "observe"`
with an approvals store that denies everything. No target, no approval, no audit block record.

A malicious or merely sloppy MCP server can therefore get an unmapped tool executed by
wording its description carefully. This is the single clearest bypass of the documented model.

**Fix:** untrusted tools should default to `active` (or be refused entirely) unless the operator
maps them. Classify on `tool.name` only, anchor the passive patterns, and require a
`capabilityMap` entry for *any* execution rather than only for non-passive. Precedence should
also be re-ordered so a destructive-looking name is never rescued by a passive-looking
description.

### H3 — Rate limiting does not hold under concurrency
`src/mcp.mjs:#throttle`

```js
const wait = this.#lastRequest + interval - Date.now();
if (wait > 0) await sleep(wait);
this.#lastRequest = Date.now();
```

All in-flight callers read the same `#lastRequest`, compute the same `wait`, sleep in parallel,
then all write `#lastRequest`. Measured with `requestsPerMinute: 6` (interval 10 s) and five
concurrent calls: **10.0 s total, not 40 s**. The limit is effectively per-burst, so with
`maxParallel: 2` the real ceiling is ~2× the configured rate — and `README`/`SECURITY.md` both
list "request-rate controls" as a hard guarantee against a target being hammered.

**Fix:** reserve the slot before awaiting — advance `#lastRequest` to
`max(now, #lastRequest + interval)` synchronously and sleep until that timestamp.

## 4. Medium severity

### M1 — Documented approval target syntax never matches
`src/approvals.mjs:wildcard` supports only a trailing single `*` (prefix match). Both
`README.md:239` and `docs/BURP.md:208` instruct the operator to run:

```bash
webcat approvals grant --target 'https://app.example.test/**' ...
```

Verified: that approval does **not** permit `https://app.example.test/account`
(`permits() → false`), while `--target 'https://app.example.test/*'` does. The engagement file
uses `/**` glob semantics (`pathMatches` handles `**` properly), so the two syntaxes disagree.
The operator's copy-pasted approval silently does nothing and the operation is refused —
fail-closed, so not a security hole, but it will be debugged as "approvals are broken".

**Fix:** reuse the `pathMatches`-style glob for approval targets (support `**`), or at minimum
correct both docs and reject a `--target` containing `**` with a clear message.

### M2 — Policy rejections other than scope are not audited
`McpGuard.call` appends `mcp.blocked` only when `evaluateScope` fails. The untrusted-active
rejection, the missing-target rejection, the approval-required rejection, and the
`maxParallel` rejection all `throw` with no audit entry. The hash-chained audit is presented as
the record of what the system refused; right now it records only one of five refusal classes.

### M3 — Full-file rewrite of the audit log on every append
`src/audit.mjs:#append` reads all entries, pushes one, and rewrites the whole file with a
non-atomic `writeFile`. Two consequences: quadratic cost (measured: 200 appends cost 181 ms at
~200 entries, 448 ms at ~800 — and a real engagement will produce thousands), and a crash or
disk-full mid-write truncates or destroys the *entire* chain rather than losing one line.
A corrupt file also makes every subsequent `append` and `verify` throw permanently.

**Fix:** keep the head hash in memory, `appendFile` a single line, and write via temp-file +
`rename` if a rewrite is ever needed. `verify()` can still stream the file.

### M4 — Redaction misses secrets in raw HTTP text
`redact` masks by *object key*, and `redactText` only handles `bearer …`, `key/token/password/secret =|:` and
a few query parameters. Burp evidence arrives as a raw request/response **string**, where
verified misses include:

```
Cookie: session=abc123           → not redacted
Authorization: Basic dXNlcjpwYXNz → not redacted (only "bearer" is matched)
eyJhbGciOi…JWT in a body          → not redacted
```

Since `EvidenceStore.add` persists this to disk at `0600` and the audit log embeds it, live
session cookies and Basic credentials for the target application end up in plaintext files.
`SECURITY.md` claims "WebCat redacts common secret fields before writing logs, evidence, and
audit records" — `Cookie:` is about as common as it gets.

**Fix:** add header-line patterns (`^(cookie|set-cookie|authorization|proxy-authorization|x-api-key):`,
case-insensitive, multiline) and a JWT pattern to `INLINE_PATTERNS`.

### M5 — `filterOutOfScope` discards whole result trees
Any object whose subtree contains a single out-of-scope URL is replaced by `undefined`, and
because the check runs at every level, one foreign URL poisons its ancestors. Verified:

```js
{ items: [ {url: "https://app.example.test/a"}, {url: "https://cdn.other.test/lib.js"} ] }
// → undefined   (the in-scope entry is lost too)
```

Real proxy history almost always references a CDN, an analytics host, or an external font, so
a typical `get_proxy_http_history` result will collapse to nothing and the agent will
reason from an empty evidence set without any signal that filtering occurred. Prefer pruning
the offending leaf/sibling and attaching a `{ filtered: n }` marker so the omission is visible.

### M6 — `--opt=value` is silently ignored
`cli-utils.mjs:positionals` drops any token starting with `--`, and `flag()` only reads
`args[index + 1]`. So `webcat scope-check https://x.test --operation=active` is evaluated as
**passive** and prints an "allowed" verdict for the wrong operation class. For a command whose
only job is answering "may I do X to Y", answering about a different X is a real hazard.
Reject unknown `--`-tokens, or parse the `=` form.

## 5. Low severity / polish

- **`tokenize` breaks JSON args in the TUI.** It strips quotes unconditionally, so
  `mcp call burp t --args '{"a":1}'` becomes `{a:1}` and fails `JSON.parse`. `mcp call` is
  effectively unusable from the TUI that the README advertises.
- **MCP config accepts an empty command.** `${MISSING_VAR}` interpolates to `""` and
  `validateMcpConfig` passes (`typeof "" === "string"`), producing an obscure `spawn`
  failure later. Validate non-empty after interpolation, or warn on unresolved variables.
- **Version is duplicated** in `src/mcp-transports.mjs:151` (`clientInfo.version: "1.1.0"`)
  instead of reading `IDENTITY.version`; it will drift at the next release.
- **`bin/webcat.mjs` exits 13 with "unsettled top-level await"** when the TUI receives EOF
  (`webcat tui < /dev/null`). Handle `question()` rejection / stdin close and return 0.
- **`SessionStore.write` mutates the caller's object** (`session.updatedAt = …`) — fine today,
  surprising later.
- **`EvidenceStore.truncate`** compares byte length but slices by characters, so the preview can
  exceed `maxBodyBytes` for multi-byte content.
- **`toolCache` is never invalidated**, so a long-running TUI session will not see tools added
  after a Burp extension reload. A `webcat mcp refresh` would help.
- **npm metadata is incomplete** for a public package: no `repository`, `bugs`, `homepage`, or
  `keywords`. There is also no `CHANGELOG.md` despite a versioned "1.1" release narrative.

## 6. Tests, QA, and CI

The gate is well-composed for a dependency-free project and the smoke/relocation tests are a
nice touch — but the labels overstate what runs:

- **`npm run lint` is `node --check`.** That is a syntax parse, not linting. No unused-variable,
  no-floating-promise, or no-fallthrough checking. Consider `eslint` (dev-only dependency) or at
  least document it as "syntax check".
- **`npm run typecheck` imports modules and asserts seven exports exist.** There is no type
  checking. `checkJs` + JSDoc via a dev-only `typescript` would catch the `hosts: "string"`
  class of bug from H1 at author time.
- **27 tests, no coverage measurement.** Add `node --test --experimental-test-coverage` with a
  floor. The untested areas map closely to the findings above: allow-rule validation,
  `#throttle` under concurrency, `filterOutOfScope` mixed-scope trees, redaction of raw HTTP
  text, and audit behaviour on a corrupt file.
- **CI is single-platform, single-Node.** `paths.mjs` branches on `win32`/`darwin` and is only
  exercised through simulated `platform` arguments. A `strategy.matrix` over
  `ubuntu/macos/windows` × Node `22/24` is cheap and would validate the real path code and the
  `0o600`/`0o700` mode assumptions (which are no-ops on Windows — worth a doc note).
- **No supply-chain / static analysis jobs.** Even at zero dependencies, `permissions: contents: read`
  plus CodeQL and Dependabot (for GitHub Actions versions) is standard hygiene for a security tool.
- **No integration test asserts a *refusal*.** `smoke.mjs` only walks the happy path. A smoke
  case that attempts an out-of-scope active call and asserts a non-zero exit plus an
  `mcp.blocked` audit entry would protect the product's core promise.

## 7. Documentation

Accurate and unusually honest overall — the "Current limitations" and "Safety boundary"
sections are exactly right, and the docs/ set is well-partitioned. Corrections needed:

1. `README.md:239` and `docs/BURP.md:208` — the `/**` approval target does not work (M1).
2. `SECURITY.md` — "redacts common secret fields" overstates current behaviour for raw
   HTTP text (M4).
3. `README.md` / `docs/SECURITY_MODEL.md` — "Rate and concurrency limits" should be qualified
   until H3 is fixed.
4. `docs/RELEASE_QA.md` — describes `qa` as performing "syntax linting, module contract checks";
   that is honest, but the README's "Development and QA" section reads as though `lint` and
   `typecheck` are conventional. Worth one clarifying sentence.
5. `.webcat/*.example.*` files exist in the repo but are never referenced from the docs; either
   link them from `docs/CONFIGURATION.md` (which is only 19 lines and could use the examples)
   or drop them.

## 8. Suggested order of work

1. H2 (untrusted-tool classification) — closes the one true bypass.
2. H1 (allow-rule validation) — closes the one true misconfiguration fail-open.
3. H3 (throttle) + M2 (audit the other refusals) — restore the documented guarantees.
4. M4 (raw-HTTP redaction) — prevents live credentials landing on disk.
5. M1, M5, M6 — correctness/usability bugs that will otherwise be reported as breakage.
6. M3 (append-only audit) before anyone runs a long engagement.
7. Test/CI hardening: coverage floor, refusal-path smoke test, OS matrix, real lint.

Each of H1–H3 and M1–M6 is a small, self-contained change; I can implement them with
accompanying allow/deny tests in the order above if you'd like.
